# AGENTS.md — pkg/clients

Instrumented Kubernetes client wrappers. See [docs/context/shared/client-access.md](../../docs/context/shared/client-access.md)
for the `pkg/client` vs `pkg/clients` distinction and when to use which. This file covers implementation detail.

## `dclient` has no decorators of its own — but it isn't actually an observability gap in production

`pkg/clients/dclient.Interface` (in `client.go`) is a generic dynamic/discovery client, hand-maintained, with no
metrics, tracing, or logging wrapping of its own — confirmed by grep, it has no `WithMetrics`/`WithTracing`/
`WithLogging` methods at all, unlike every generated client here. That sounds like a real observability gap, and in
isolation it would be — but in every controller binary, `dclient` is constructed by `cmd/internal.Setup`
(`createKyvernoDynamicClient`, `cmd/internal/client.go`), which passes it a `dynamic.Interface` and
`kubernetes.Interface` that were *already* wrapped with `WithMetrics(...)`/`WithTracing()` a few lines earlier in
`cmd/internal/setup.go`. `dclient` just holds and delegates to those (`client.dyn`/`client.kube` in `client.go`), so
ordinary resource calls made through `dclient` in `cmd/kyverno`, `cleanup-controller`, `reports-controller`, and
`background-controller` do carry metrics/tracing — it's delegated instrumentation, not decorated instrumentation.
The gap is real only for `dclient` instances built *outside* `cmd/internal.Setup`: `cmd/cli/kubectl-kyverno`'s
`apply` command and `ext/cluster.New` both call `dclient.NewClient` directly with raw
`kubernetes.NewForConfig`/`dynamic.NewForConfig` clients, no metrics/tracing wrapping at all. If you're debugging
missing traces/metrics for dynamic-resource calls, check which of these two construction paths you're on before
assuming it's a `dclient`-wide limitation.

Most of the rest (`kube`, `kyverno`, `apiserver`, `aggregator`) is fully generated by `hack/client-wrapper` via
`make codegen-client-wrappers`, in three layers per resource: resource-level `WithLogging`/`WithMetrics`/
`WithTracing` decorators around each verb, client-level wrapping per API group, and a top `Interface` (embeds the
upstream interface plus composable `WithMetrics(...)`/`WithTracing()`/`WithLogging(logger)` methods you call at
construction time). `dynamic` and `metadata` are a hybrid: their `resource.generated.go` and `interface.generated.go`
come from the same generator, but each package's `client.go` is hand-written — `hack/client-wrapper/main.go`'s
`main()` never calls `generateClientset` for these two, because `dynamic.Interface`/`metadata.Interface`'s
navigational `Resource()`/`Namespace()` methods aren't templatable the way a flat clientset is (the hand-written
file implements `WrapWithMetrics`/`WrapWithTracing`/`WrapWithLogging` manually instead). None of the generated files
in this package (nor `dclient`, nor the two hand-written `client.go` files) currently carry a `// DO NOT EDIT`
header (unlike every other generated zone in the repo) — treat the generated ones as no-edit anyway;
`.claude/settings.json`'s `permissions.deny` enforces this by path for Claude Code sessions regardless of the
missing header.

## `dclient`'s discovery cache is genuinely stateful and self-invalidating

`NewClient` wires a memory-cached discovery client and starts a background goroutine (`discoveryClient.Poll`) that
periodically invalidates the cache — the comment explains why: "there is no way to identify if the registered
resource is available or not." If CRD-watcher mode is enabled, a second goroutine watches CRDs directly and
invalidates on change. GVR resolution is explicitly commented as stateful — **which GVR a given apiVersion/kind
resolves to can change at runtime** as CRDs are added or removed; don't assume a resolved GVR is a compile-time
constant.

`ApplyResource`/`ApplyStatusResource` use a field manager prefixed `"kyverno-"` with `Force: true`, so that *this*
apply succeeds and claims ownership of the fields it sets even if another manager currently owns them, rather than
failing on a server-side-apply conflict. This isn't a standing guarantee — a later forced apply or update from
another manager can still overwrite those same fields; `Force: true` only resolves the conflict at the moment of
Kyverno's own write.
`RawAbsPath` only supports GET/POST for real clients; under the fake client (tests) it falls back to a separate,
hand-rolled path parser that's GET-only — don't assume `RawAbsPath` test coverage extends to POST or to real-client
path-parsing edge cases.

## When you actually need to re-run `make codegen-client-wrappers`

The generator reflects over exactly six upstream client interfaces (`kubernetes.Interface`, this repo's own
generated `pkg/client/clientset/versioned.Interface`, `dynamic.Interface`, `metadata.Interface`, the
apiextensions-apiserver clientset, and the kube-aggregator clientset). Re-run it when: a new Kyverno CRD/API
resource is added (changes the versioned clientset), a `client-go`/`apiextensions-apiserver`/`kube-aggregator`
version bump adds new methods, or new methods are added to `dynamic.Interface`/`metadata.Interface`. **It does not
touch `dclient`** — that package is edited by hand, and adding a method to `dclient.Interface` is a manual change,
not a codegen output.
